# 第二轮优化实施计划：编排、工具、记忆与后端效率

日期：2026-07-26
依据：四领域优化分析（节点编排 / 工具调用与 MCP / 记忆系统 / 后端效率）+ 7-26 真实评测数据。
基线（必须先记录，所有改动与之对照）：20 题标准评测 avg 21.3s、sql_generation 7.16s、记忆检索规划 12ms、rewrite 候选 19/20、fast_path 命中 0、执行成功 19/20；测试 349/349。

## 阶段一：记忆生命周期（最高杠杆，预期中位延迟 20s → 数秒级）

**1a. 自动可信升级。** `sql_memories.trust_status` 增加状态机：同一 normalized_question 连续 N 次（默认 3）执行成功、行形状稳定、context_fingerprints 一致 → 自动升级 `verified`；任一次执行失败或指纹漂移 → 降级 `pending` 并记录原因。实现位置：`update_memory` 节点内升级判断 + `memory_repository` 状态字段迁移（017 migration）。

**1b. 管理动作补全。** SqlMemoryPage 增加"标记可信 / 撤销可信"操作（walking API 已有仓储方法则补 API 路由），管理员可人工纠偏。

**1c. 记忆异步化。** `update_memory` 与 `log_run` 移出关键路径：`present_result` 后即返回响应，落库工作提交后台线程（有界队列 + 失败日志）。实测该节点 4.6s，为纯事后簿记。

**1d. Few-shot 注入。** 生成提示词加入 top-2 verified 记忆的（问题, SQL）对作为示例；无 verified 记忆时退化为现状。控制增量 token（示例 SQL 截断至 ~40 行）。

**验收：** 预置 3 条 verified 记忆的 warm 评测 fast_path 命中 ≥ 3；连续三次重复同一问题后第四次走 fast_path；全量测试绿；新增测试覆盖状态机（升级/降级/指纹漂移）与异步落库（响应先于落库完成）。

## 阶段二：图编排（依赖 1a，冷路径与整体时延）

**2a. 记忆优先重排。** 图入口顺序改为：embed → 记忆检索与规划 → 若 verified fast 命中：跳过意图 LLM 与上下文检索，直接 guard→explain→execute；未命中再走现有完整链路。注意 fast 命中路径仍需 result_contract 与呈现所需的最小上下文（从记忆记录携带 tables/metrics）。

**2b. 并行分支。** 冷路径下意图解析（LLM）与上下文检索（embedding+DB）并行，fan-in 后进入记忆规划；路由 LLM 调用在意图解析必然执行时跳过。

**2c. 修复预算优化。** repair 提示词只携带失败约束的 AST 差异；错误分类为"空结果/数据侧"时不触发 repair；新增 best-of-N（N=2，温度 0 / 0.4）并行候选 + 执行择优，仅在冷路径启用。

**2d. 取消令牌。** SSE 断连时置 cancel event，节点间检查点提前退出，释放线程池。

**验收：** 重复问题端到端 ≤ 3s；冷路径 avg 相对基线 −20% 以上（同日同端点对照）；断连后 5s 内后端停止后续节点（日志验证）。

## 阶段三：工具层与 MCP

**3a. ToolResult 统一契约。** `{status, latency_ms, diagnostics, payload}`，所有 tools 返回统一结构；`_log_analysis_run` 的手工日志组装改为自动汇集。

**3b. 受限工具回合。** SQL 生成前允许模型最多 1 轮工具调用：`sample_values(table, column)`（枚举列 TOP 值）与 `schema_detail(table)`；OpenAI function-calling 协议经现有 ModelAdapter。设置总超时与白名单，失败静默退回一次性生成。

**3c. MCP 服务端（展示型，可后置）。** 以 MCP 协议包装 guard+execute+schema 三工具（stdio server），README 附 Claude Desktop 配置示例。

**验收：** 3a 后 run 详情页字段不变（对比快照）；3b 在 20 题集上 keyword/table match 不降且 wrong-literal 类失败（如 status 取值错误）用例修复 ≥1；工具回合平均额外耗时 ≤ 1.5s。

## 阶段四：后端效率与运维

**4a. 索引与清理。** 017 migration：三张 embedding 表 HNSW（vector_cosine_ops）、`auth_sessions(token_hash)` 唯一、`conversation_states(owner_id, updated_at DESC)`、`tool_calls(query_run_id, created_at)`、`sql_memories(normalized_question)` 唯一 + upsert 改 `ON CONFLICT`；每日清理任务（过期会话、90 天前 runs/tool_calls）。

**4b. 会话存储瘦身。** 列表只查列不反序列化 state；保存改 `jsonb_set` 追加消息（或消息表，二选一，以改动小者优先）。Redis 层裁决：删除（当前为纯开销）。

**4c. Embedding 韧性。** 归一化问题 → 向量的进程内 LRU（512 条）+ 可选 SQLite/表级持久缓存；`EMBEDDING_FALLBACK_PROVIDER=deterministic` 供端点故障降级（附告警日志）。

**4d. 运维项。** `/api/analyze` 响应体返回 run_id（评测链路改用之）；报告写入原子替换失败重试（上次 Windows 现象）；evaluation 页展示 tool_calls p95。

**验收：** EXPLAIN 验证向量查询走 HNSW；100 轮会话写入耗时对比（瘦身前后）；埋点显示 embedding 缓存命中率；评测 run 关联 100% 使用 run_id。

## 顺序与风控

1a→1c→2a 是主线（每步全量测试 + 20 题评测对照，同一天跑基线与对照以排除端点波动）；2b/2c、3a/3b、4a–4d 可穿插独立提交。所有 migration 向后兼容（新增列/索引，不改既有语义）；图重排保留旧路径开关（`GRAPH_MEMORY_FIRST=true|false`）以便回退对照。

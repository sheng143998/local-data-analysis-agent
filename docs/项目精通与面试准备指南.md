## 一、电梯陈述（背到脱口而出）

**30 秒版：** "我做了一个本地部署的数据分析 Agent：业务人员用中文提问，系统自动生成并执行 SQL，返回答案、图表和完整依据。核心是一条 LangGraph 编排的十二节点流水线——意图解析、语义契约、混合检索、模型生成 SQL、AST 级安全校验、只读执行、SQL 记忆复用。它有完整的评测体系和 349 个自动化测试，我用评测数据驱动做了两轮优化，比如把每次请求的 embedding 调用从 4 次降到 1 次、记忆检索从 1.3 秒降到 12 毫秒。"

**2 分钟版（在 30 秒版之后接）：** "这个项目最让我有收获的是三件事。第一，**确定性与模型能力的边界划分**：模型只负责把意图翻译成 SQL，而能不能执行由确定性的 Guard 裁决——sqlglot 解析 AST，拦截写操作（包括藏在 CTE 里的 DELETE）、白名单外的表、危险函数，最后在只读事务里执行。第二，**评测先行**：我发现默认评测的 95% '严格通过率'其实没有做答案校验，真实的 ground-truth 准确率只有 26%——指标失真会让所有优化瞄错方向，所以我先修评测再做优化。第三，**用数据定位瓶颈**：per-node 计时显示 SQL 生成占 8 秒、记忆簿记 4.6 秒在关键路径上、同一个问题被 embedding 了 4 次，针对这些做的重构在真实评测里得到了验证。"

**一句话定位（面试官问"这是个什么类型的 Agent"）：** "它是一个**工作流型（workflow-based）Agent**，不是自主循环型（autonomous）——控制流由图确定，模型在关键节点做翻译和修复。对企业数据这种高风险场景，我认为可预测性比自主性重要，这是一个刻意的架构选择。"

## 二、必背数字（面试前一晚过一遍）

**规模：** 后端 ~60 个 Python 模块、12 个图节点、16 个数据库迁移、349 个自动化测试（约 3 分钟跑完）；前端 React + TS，tsc 零错误；评测集 20 题标准 + 50 题 ground-truth + 100 题综合。

**评测真相：** 标准 20 题执行成功 19/20（95%）——但这是结构性指标；带答案校验的 50 题基线：执行 62%、严格 26%、答案匹配 29%。（这组数字主动讲，是你"评测素养"的证据。）

**延迟画像（优化前，20 题平均）：** 端到端 19.8s（p50 18.8 / p95 29.7）；SQL 生成 8.15s、未归因 5.2s、上下文检索 2.8s、记忆检索+更新 2.8s、DB 执行仅 142ms——瓶颈全在模型与网络，不在数据库。

**优化成果（真实复测）：** SQL 生成 8.15→7.16s（−12%，提示词去重）；记忆检索规划 1354→12ms（−99%，embedding 一次化+连接池）；每请求 DB 连接 15~25 个→池化复用；tool_calls 日志 10 连接→1 批量；rewrite 候选命中 19/20。**warm 实验：** 记忆命中时端到端 29.1→13.9s（−52%），SQL 生成归零——这是下一轮"记忆生命周期"优化的依据。

**安全修复：** Guard 首关键字检查可被 `WITH d AS (DELETE ...) SELECT` 绕过 → AST 遍历修复；比率二次放大 bug（1.24% 显示 124.00%）。

**记忆三路径阈值：** fast ≥ 0.88 且 verified 且指纹一致；rewrite ≥ 0.70；否则 cold。评分权重：语义 0.45 / 词面 0.25 / 表指标匹配 0.20 / 历史成功率 0.10。

## 三、架构走查（要求自己能白板画出）

**一条问题的完整旅程（按此顺序讲）：**

1. **对话路由（dialogue_router）**：闲聊/越界/数据问题三分类，小模型+规则兜底。
2. **意图解析（question_intent_parser）**：LLM 输出结构化意图（指标、维度、时间、过滤），置信度低走澄清。
3. **语义契约（semantic_resolver + contracts 表）**：把"复购率""毛利率"绑定到已审核的口径定义（source_tables/fields、聚合方式）——这是防"指标口径幻觉"的核心。
4. **查询规划（query_planner）**：意图+契约 → QueryPlan（entities/measures/dimensions/order/limit/execution_contract）。
5. **混合检索（context_builder）**：指标定义 + schema 元数据 + 外键关系；打分 = 关键词 + pgvector 语义 + 文本相似度加权，再 rerank。
6. **SQL 记忆规划（sql_memory_tools）**：向量+词面+表指标+成功率四信号打分，三路径决策。
7. **SQL 生成（model_sql_generator）**：结构化 JSON 提示词（计划为必须约束、召回为候选知识），qwen 系模型输出 JSON 格式 SQL。
8. **意图校验（Inspector + AST 校验器）**：计划要求的表/度量/时间边界是否满足——基于 sqlglot AST，不是正则。
9. **修复（repair，各限 1 次）**：把校验/执行错误结构化喂回模型。
10. **Guard（sql_validation_tools）**：单语句、仅 SELECT、AST 无写节点、表白名单、字段存在性、禁 SELECT *、危险函数黑名单、LIMIT 钳制。
11. **EXPLAIN 预检 → 只读事务执行**（statement_timeout + BEGIN READ ONLY + rollback）。
12. **呈现与记忆回写**：结果契约 → 摘要/图表配置/指标卡；成功 SQL 连同指纹写回记忆；全链路 run + tool_calls 落库。

**分层一句话：** API（FastAPI+SSE）→ 服务层（会话/认证/Agent）→ 图编排（LangGraph）→ 工具层（纯函数，可单测）→ 仓储层（pg8000+连接池）→ PostgreSQL+pgvector。**"工具层是纯函数"** 值得强调：349 个测试大部分不需要 mock 网络就能跑。

## 四、设计决策问答（每条：决策 → 理由 → 权衡）

**Q：为什么用 LangGraph 而不是让模型自主 ReAct 循环？** 决策：确定性图编排。理由：数据分析结果要可信、可审计、可复现；自主循环的失败模式（死循环、跳步、幻觉工具调用）在这个场景不可接受。权衡：牺牲了开放任务的灵活性——所以在下一轮里我给生成节点加"受限工具回合"（最多 1 轮 sample_values/schema_detail），在图的框架内引入局部自主性。这个"频谱观"（workflow ↔ autonomous）是面试高频考点。

**Q：为什么语义契约（semantic contracts）？** 模型最常见的错不是语法而是**口径**：把"已支付"写成 orders.status='paid'（该表根本没有 paid）。契约把业务定义前置为数据（表+版本+来源字段+聚合），生成时作为硬约束注入，校验时作为标准检查。等价于把"业务知识 RAG 化 + 合同化"。

**Q：安全为什么是多层的？单靠提示词行不行？** 不行——提示词是建议，不是边界。五层：提示词约束（软）→ AST 校验（禁写/白名单/字段存在）→ LIMIT 钳制 → EXPLAIN 预检 → 只读事务执行。我实际修过一个绕过：首关键字检查放行了 `WITH d AS (DELETE ...) SELECT`，AST 遍历才是正解。讲这个案例 = 展示纵深防御思维。

**Q：检索为什么是混合（hybrid）而不是纯向量？** 表名/指标名是短文本专有名词，词面匹配信息量大；语义分补足同义表达（"成交额"→sales_amount）。四信号加权 + rerank。且向量检索失败时静默降级到词面——但我给降级加了告警日志，"静默降级不可观测"是我踩过的坑。

**Q：SQL 记忆为什么三路径？** fast（verified 直用，省掉整条 LLM 链）/ rewrite（相似 SQL 作参考重生成）/ cold（全新）。信任维度独立于相似度：相似 ≠ 可信，所以 fast 额外要求 trust_status=verified + 上下文指纹一致（schema 变了就失效）。当前短板是 verified 从未自动授予 → 命中 0，这正是我第二轮计划的第一项（讲出来，显示你知道系统真实状态）。

**Q：为什么 SSE 而不是 WebSocket？** 单向流式推送（阶段事件+结果），SSE 足够且更简单，POST+fetch-stream 实现，配合每事件空闲超时与取消。双向才需要 WS。

**Q：评测怎么设计的？** 三层：pytest（单元/集成，349 个）→ 批量评测（JSONL 数据集 + 断点续跑 + 报告 JSON）→ 专项实验（warm/cold 对照）。指标分执行性（跑没跑通）与语义性（答案对不对），我修过"严格通过率虚高"的指标缺陷。加分句："我把评测当产品做——指标失真比没有指标更危险。"

**Q：本地小模型 vs 云端大模型怎么权衡？** 模型路由按角色配置：路由/意图可用小模型，生成用强模型；数据不出域时全本地（Ollama qwen2.5-coder），追求准确率时用云端 qwen-max。适配层统一 OpenAI-compatible 协议，切换零代码改动。

## 五、优化叙事（STAR 化，挑 2~3 个讲透）

**① 连接池与 embedding 一次化（性能）。** S：评测显示非模型耗时异常高。T：定位并消除基础设施浪费。A：读代码发现每次请求建 15~25 个裸 TCP 连接（日志一项就 11 个）、同一问题被 embedding 3~4 次；实现线程安全有界连接池（借出/归还/损坏丢弃/归还前 rollback）、问题向量入图状态全链复用、日志批量 executemany。R：记忆检索规划 1354→12ms；测试套件 72→31s；真实评测复测验证。**追问准备**：池满策略（新建临时连接，归还时溢出即关）、连接损坏检测（异常路径直接丢弃不回池）、为什么不直接换 psycopg pool（保持依赖不变、行为可控，且这是教学型项目我想自己写一遍）。

**② Guard 写操作绕过（安全）。** S：审计安全层。T：验证"模型输出无法绕过确定性防线"的承诺。A：构造 `WITH d AS (DELETE FROM orders RETURNING id) SELECT ...`——首关键字是 WITH、顶层是 Select、表在白名单内，旧 Guard 放行；修复为 AST 遍历 find_all(Insert/Delete/Update/...)+SELECT INTO 检查+函数黑名单扩充，并写了攻击用例测试。R：五层防线补上唯一依赖单点的环节。**这是最能打动面试官的故事**：主动构造攻击 → 修复 → 回归测试。

**③ 评测指标失真（工程判断）。** S：默认评测 95% 严格通过 vs ground-truth 26%。T：解释矛盾。A：读评测代码发现 `answer_match is not False` 在无期望答案时空洞通过、表匹配是子串匹配（users 能被 users_snapshot 匹配）。R：先修指标再谈优化——"如果我按 95% 去优化，就是在优化一个不存在的东西。"

**④ 比率二次放大（细节敏感度）。** 前端截图发现 1.24% 显示成 124.00%；表格对、摘要错 → 定位到 presenter 假设数据库返回 0~1 小数，而项目 SQL 口径统一输出 ×100；修复加量纲启发式 + 两个回归测试，并指出长期解是结果契约携带显式单位。展示：从 UI 症状反推数据流分层定位。

## 六、通用面试题库与答法（题目主题综合自 DataCamp、GeeksforGeeks、InterviewBit、UPenn Career Services、Exponent、IGotAnOffer 等公开题库，见文末来源）

**答题总原则：定义（1 句）→ 机制（2~3 句）→ 本项目佐证（1~2 句）→ 权衡/局限（1 句）。** 每道题的最后一步是把话题拉回你的主场。

### A. Agent 基础

- **什么是 Agentic AI / 与传统 AI 的区别？** 要点：感知-推理-行动闭环、目标导向、工具使用、（可选）自主规划；区别于单轮问答的被动生成。佐证："我的项目是把 LLM 嵌入十二节点闭环：解析→检索→生成→校验→执行→反馈修复→记忆沉淀。"
- **Agent 的核心组件？** LLM（推理）、工具（行动）、记忆（状态）、编排（控制流）、护栏（边界）。逐一映射你的模块名。
- **什么是 ReAct？** Reasoning+Acting 交替：思考→选工具→观察→再思考。答完必接："我刻意没用开放式 ReAct，而是图编排+局部工具回合，因为高风险数据场景要可预测性"——把知识题转成判断题。
- **Workflow 型 vs Autonomous 型？** 频谱而非二元：控制流在代码 vs 在模型。选择依据是任务风险与失败成本。
- **任务分解（task decomposition）？** 你的 query_planner 就是结构化任务分解：问题→实体/度量/维度/约束。
- **多智能体（multi-agent）？** 诚实回答未在本项目用到 + 说清何时需要（角色分工、辩论校验、并行探索）+ 你的单 agent 内部其实有"生成者/校验者"对抗结构，是 multi-agent 思想的图内实现。

### B. 工具调用 / Function Calling / MCP

- **什么是 tool use / function calling？** 模型输出结构化调用意图，运行时执行并回填结果。区分：协议（OpenAI tools 格式）vs 编排（谁决定调用）。佐证：你的工具由图确定性调用 + 二轮计划中的受限工具回合。
- **什么是 MCP？为什么需要？** Model Context Protocol：把"模型↔工具/数据源"的接口标准化（类比 USB-C/LSP），解决 M×N 集成问题；host/client/server 架构，server 暴露 tools/resources/prompts。佐证：你的计划是把 guard+execute+schema 包成 MCP server，让任意客户端共享同一安全层。
- **工具调用失败怎么办？** 超时、重试白名单（只重试瞬态错误——引用你把 4xx 从重试中剔除的改动）、降级路径、结构化错误回喂修复。

### C. RAG / 检索

- **什么是 RAG？解决什么问题？** 用检索把外部知识注入上下文，缓解幻觉与知识时效。**关键转化**："我的检索对象不是文档段落，而是结构化元数据——schema、指标口径、历史 SQL——本质是 RAG 在结构化世界的变体。"
- **Embedding/向量检索原理？chunking 策略？** 语义向量近邻；你的"chunk"是天然结构化单元（每列一条、每指标一条），不存在切分难题——但要会讲文档场景的常规答案（固定窗口/语义切分/重叠）。
- **混合检索与 rerank 为什么重要？** 词面与语义互补；你有现成的加权公式与 rerank 层可讲。
- **RAG 怎么评测？** 检索侧（召回率/命中率——你的 present_in_context 分析：失败用例表都召回了，是生成没用上，从而把优化重心从检索转向生成）+ 生成侧（答案正确性）。

### D. 记忆系统

- **短期 vs 长期记忆？** 短期=会话状态（你的 conversation_states，200 条上限+分页）；长期=跨会话沉淀（sql_memories、long_term_memories）。
- **记忆怎么检索与更新？** 讲四信号打分、三路径、指纹失效、成功回写；更新时机（执行成功后）、并发（ON CONFLICT 计划）、遗忘（fingerprint 漂移降级——二轮计划）。
- **为什么 Agent 需要记忆？** 降本（复用验证过的 SQL 省掉整条生成链，warm 实验 −52%）、提准（few-shot）、个性化（长期偏好）。

### E. 护栏 / 幻觉 / 安全

- **如何减少幻觉？** 分层答：约束生成（结构化提示词+JSON 模式+契约）、检索接地（真实 schema）、确定性校验（AST/白名单）、执行验证（EXPLAIN+真实执行）、评测闭环。你的项目每层都有实物。
- **自主 Agent 的安全风险？**（DataCamp/GeeksforGeeks 高频）提示词注入、越权工具调用、数据外泄、资源滥用。佐证全套：只读事务、表白名单、函数黑名单、LIMIT 钳制、速率限制、CSRF/argon2id、你修的 CTE 绕过。
- **提示词注入怎么防？** 诚实分层：路由端词表只是 UX，不当安全边界；真正的边界是"模型输出进入确定性校验器"——模型说什么都行，能执行什么由 Guard 决定。
- **Human-in-the-loop？** 你的澄清机制（低置信度反问）+ 记忆人工 verify 动作 + 管理员运行审计页。

### F. LLM 工程

- **系统提示词 vs 用户提示词？** 角色与优先级分离；你的生成器：system 定规则（只输出 JSON/禁 SELECT *），user 带数据（计划+schema+问题）。
- **上下文窗口为什么有限/怎么省 token？** 注意力二次方成本；你的实战：去掉三份重复计划、metric_semantics 按需注入、去 indent（−30% token）→ 生成提速 12%，有数字。
- **温度等参数？** 生成 SQL 用 temperature 0（确定性优先）；best-of-N 时用温度多样性做候选。
- **微调 vs RAG/提示工程？** 先 RAG+提示（快、可控、无需数据集）；口径类知识用契约外置而不是烧进权重（可版本化、可审计）；微调适合风格/格式内化——你的 3B 本地模型若要提准，LoRA 微调 text-to-SQL 是合理下一步，能讲数据集怎么来（你的 run 日志就是天然语料）。
- **流式输出为什么重要？** 感知延迟；你的 SSE 阶段事件 + 前端 stepper。

### G. 评测与可观测性

- **什么是 evals？怎么评 Agent？**（DataCamp 高频）离线批量（数据集+断言+报告）/ 在线（run 日志+人工审计）；执行性 vs 语义性指标；讲你的 95%-vs-26% 故事。
- **什么是 tracing/span/LLM 可观测性？** 分布式追踪概念映射：你的 query_runs=trace、tool_calls=spans、node_timings=span 时长；靠它定位了"未归因 5.2s"。

### H. 系统设计题（"设计一个 XX Agent"）

套路五步，直接用你的项目当模板：①需求与风险界定（读多写少？错误成本？→决定 workflow vs autonomous）②数据流主链（解析→检索→生成→校验→执行→呈现）③状态与记忆（会话/长期/复用策略）④安全与降级（护栏分层、超时、fallback）⑤评测与迭代（指标、数据集、灰度）。加分项：给出延迟预算表（模型 X 秒、检索 Y 毫秒……）——你有真实数字。

### I. 基础工程题（实习必问）

- **连接池原理/为什么需要**（你手写过：讲借出-归还-损坏丢弃-上限）
- **SQL 注入与防护**（参数化查询 + 你的 AST 白名单是更强的第二层）
- **进程/线程/异步**（FastAPI sync 路由跑线程池 → 你识别过 40 线程池饥饿问题与限流方案）
- **索引原理**（B-tree vs HNSW 向量近邻；为什么向量列没索引时是全表排序）
- **认证**（session vs JWT：你选 HttpOnly cookie session + CSRF 双提交，能讲为什么不用 localStorage 存 token——XSS 面）

## 七、追问链演练（面试官会顺着挖，提前走一遍）

**链 1：** 记忆命中率为什么是 0？→ verified 从未授予 → 那你怎么设计自动授予？→（讲状态机：N 次成功+行形状稳定+指纹一致；失败即降级）→ 会不会把错误 SQL 固化？→（verified 只免生成不免 Guard/执行；答案漂移会触发降级；契约版本变更使指纹失效）。

**链 2：** 严格通过率 95% 和答案准确率 29% 差在哪？→ 结构匹配 ≠ 语义正确 → 那 29% 怎么提？→（few-shot 记忆、sample_values 工具、best-of-N 执行择优、契约扩容——每个都在你的二轮计划里）→ 怎么验证提升？→（ground-truth 集 + 同日对照消除端点波动）。

**链 3：** 为什么平均还要 20 秒？→ 生成 7 秒+修复 11 秒+embedding 网络 → 修复为什么这么贵？→（全上下文重发；改进：AST 差异化修复提示）→ 极限能到多少？→（fast 命中 2~3 秒，已有 warm 实验数据）。

**链 4：** 并发 100 用户会发生什么？→ 诚实：单机单用户定位；线程池饥饿、连接池上限、Ollama 无批处理 → 怎么改？→（analyze 专用池+信号量、连接池扩容、vLLM 连续批处理、记忆命中降模型压力）。

**链 5（行为面）：** 你和 AI 协作怎么分工？→ 诚实且加分的答案：架构决策、验收标准、数据判读是你的；AI 加速了实现与排查；举"我发现 AI 给的 95% 指标其实失真"这类你行使判断力的时刻。实习面试官非常在意你是否被工具牵着走。

## 八、如何谈不足（诚实=加分，每条接改进计划）

1. **答案准确率 29%**："这是我最想解决的问题，路径已排好：few-shot 记忆示例、取值探测工具、best-of-N 执行择优；且我先修好了度量它的尺子。"
2. **fast path 未打通**：机制验证过（warm −52%），缺的是信任生命周期，属于第二轮第一项。
3. **单用户单机定位**：企业化需要 Redis 限流、连接池扩容、模型服务批处理——能逐条说明改造点即证明你懂差距在哪。
4. **修复回路仍贵**（11.6s）：差异化修复提示 + 错误分类跳过。
5. **模型依赖外部端点波动**（embedding 当天 0.7s→4s）：缓存 + 本地 fallback 已在计划。
切忌：把不足说成"没时间做"；要说成"知道为什么暂缓、代价是什么、何时做"。

# 本地数据分析 Agent — 项目优化分析报告

日期：2026-07-26
范围：backend（FastAPI + LangGraph 流水线）、frontend（React/Vite）、eval 评测体系、工程规范。
方法：三个独立评审通道（Agent 流水线 / 后端服务与基础设施 / 前端与评测）全量阅读源码，关键结论已对照源码逐条复核。

---

## 一、总体评价

项目整体架构清晰：意图解析 → 语义契约 → 检索增强 → SQL 生成 → 确定性校验（Guard）→ 只读执行 → SQL 记忆，分层合理，测试覆盖面广（40+ 测试文件），文档齐全。安全设计上有亮点：argon2id 密码哈希、HttpOnly 会话 Cookie + CSRF 双提交、SQL 只在 `BEGIN TRANSACTION READ ONLY` 中执行。

但当前有三个结构性问题最值得优先解决：

1. **延迟被自身架构放大**：单个问题平均 19.8 秒（p95 约 29.7 秒），其中大量时间浪费在可消除的开销上——同一问题被重复 embedding 3~4 次、每次请求新建 15~25 个数据库 TCP 连接、最多 5 次串行 LLM 调用、以及 5.2 秒未归因耗时。
2. **默认评测指标是虚高的**：`npm run eval:standard` 报出的 95% "严格通过率"没有任何答案正确性校验（answer_checked_count = 0），而真实的 50 题 ground-truth 基线是执行 62% / 严格 26% / 答案匹配 29%。按默认指标优化会瞄错方向。
3. **SQL 记忆子系统在实测中收益为零**：标准 20 题评测中 memory_hit_rate = 0，fast_path 命中 0 次，却在每个问题的关键路径上花掉约 2.8 秒（检索 + 更新）。而人工验证过记忆的 warm 对比实验证明命中时总延迟可降 52%——说明机制本身有效，是命中策略没调好。

## 二、P0：高优先级（延迟与成本）

### 2.1 同一问题被重复 embedding 3~4 次

`backend/app/tools/vector_retrieval.py` 中 `_embed_question`（第 65 行）被 `retrieve_metric_vector_candidates`（25 行）、`retrieve_schema_vector_candidates`（42 行）、`retrieve_sql_memory_vector_candidates`（59 行）各自独立调用，每次都是一次对 DashScope 的远程 HTTPS 往返；记忆写入时（`sql_memory_tools.py` 约 176 行）又把问题重新 embed 一次。同一个问题字符串，一次请求最多付 4 次 embedding 的延迟和费用。

**建议**：在图入口（`_retrieve_context_node` 之前）embed 一次，把向量存入 `AnalysisGraphState`，三个检索函数增加可选 `vector=` 参数直接复用；记忆 upsert 时同样复用。预计每题节省 300~900 ms 和 2/3 以上的 embedding 费用。

### 2.2 无数据库连接池：每题新建 15~25 个 TCP 连接

`backend/app/db/connection.py` 的 `get_connection()` 每次都 `pg8000.dbapp.connect(...)` 再 `close()`（已复核，33~41 行）。一次分析请求会顺序触发：会话校验（2 次）、指标/Schema/记忆三路向量检索、外键内省、Guard 的字段加载、EXPLAIN、正式执行、记忆写入、会话状态 upsert，以及 `_log_analysis_run` 里 `create_run` + 约 10 次 `log_tool_call` **每次一个新连接**。粗算每题 15~25 次完整 TCP + 认证握手，本机也能贡献 0.5~1.5 秒，并发稍高就会打满 Postgres `max_connections`。

**建议**：在 `get_connection()` 背后加一个模块级线程安全连接池（简单的有界 `queue.Queue` 池即可，或换 `psycopg[pool]`）；`tool_calls` 的 10 余条日志合并到一个连接里 `executemany` 批量插入。

### 2.3 LLM 调用链最多 5 次串行，且可并行的检索是串行的

最坏路径：dialogue_router 路由（1）→ 意图解析（2）→ SQL 生成（3）→ 意图修复（4）→ 执行修复（5），全部串行，叠加 2.1 的 3 次 embedding。评测显示 sql_generation 单项平均 8.15 秒、触发 repair 的用例平均再加 9 秒。

**建议**（按性价比排序）：
其一，意图解析已能区分模糊/明确问题时跳过 router 的那次 LLM 调用；其二，上下文检索节点与记忆检索节点没有数据依赖，可用 LangGraph 并行分支或线程池并发执行；其三，对 `parse_question_intent` 按（问题, 契约指纹）做缓存，评测和仪表盘重复问题时直接命中。

### 2.4 记忆更新在关键路径上，且 26% 延迟未归因

`memory_update` 平均 1.4 秒发生在响应返回之前，但它纯属事后簿记，应改为响应后异步执行（fire-and-forget 或后台任务）。另外评测报告里平均每题有 5.17 秒 "unattributed"（API 总耗时减去所有已计时节点，占 26%），run_eval 注释推测是"Router/会话/网络等边界"——建议给 router 调用、会话持久化、run 日志各加节点计时器，把这 5 秒找出来再动手。结合 2.1~2.3，P50 延迟砍半是现实目标（warm 记忆对比实验已经演示过 29.1s → 13.9s）。

### 2.5 SQL 记忆命中率为 0，近似命中也被重新生成

标准评测 fast_path 命中 0 次；speed_006 报告里 memory_score 高达 0.9426 的用例仍走了 "regenerate"。同时 `sql_memory_tools.py` 第 47 行 `repo.list(limit=100)` 每题全量拉取最近 100 条记忆在 Python 里打分——既是 O(N) 扫描，又让第 101 条之后的记忆永久不可达。

**建议**：复盘 reuse 阈值与 fingerprint 匹配条件（0.94 的近似命中应至少走 rewrite 而非完全重生成）；检索只取向量候选 ID 并集 + 小的近期窗口；给 `sql_memories.normalized_question` 建唯一索引，用单条 `INSERT ... ON CONFLICT DO UPDATE`（`success_count = success_count + 1` 在 SQL 里算）替换现在跨两个 autocommit 连接的读-改-写（并发下会产生重复行、丢失计数）。

## 三、P0：高优先级（正确性与安全）

### 3.1 SQL Guard 存在 CTE 写操作绕过

`sql_validation_tools.py` 的写操作检测只看首关键字（`_starts_with_write_keyword`，188 行，已复核），AST 层面没有检查写节点。`WITH d AS (DELETE FROM orders RETURNING id) SELECT id FROM d LIMIT 1` 以 `WITH` 开头、解析为 `exp.Select`、只引用白名单表——Guard 会放行。目前唯一拦住它的是执行器的只读事务，防线只剩一层；`BLOCKED_FUNCTIONS` 也缺 `pg_terminate_backend`、`pg_cancel_backend`、`lo_import/lo_export`、`set_config`。

**建议**：在 `validate_sql` 里对 AST 做 `expression.find_all(exp.Insert, exp.Delete, exp.Update, exp.Merge)` 检查，同时拒绝 `SELECT ... INTO`，补全函数黑名单。这是文档承诺的"模型输出无法绕过确定性安全工具"真正需要的实现。

### 3.2 正则/子串式意图校验产生假阳性修复循环

`analysis_graph.py` 里的 `_token_present`（约 1001 行）把表别名写死（如 `count(distinct u.id`——别名不是 `u` 的正确 SQL 会被判"缺少指标口径"）；`_sql_has_time_bounds`（约 1274 行）不认 `::date` 转换、`BETWEEN`、操作数反序等 PostgreSQL 惯用写法；`_context_table_coverage` 会因为检索多召回了表就要求 JOIN 进去，与提示词里"不要仅因其存在而 JOIN"自相矛盾。每次误报 = 一次多余的修复 LLM 调用（数秒），还可能把正确 SQL 改坏。这是全流水线里正确性和延迟耦合最重的一处。

**建议**：改用 `sql_inspector.py` 里已有的 AST 别名解析逻辑（`_table_aliases`/`_referenced_fields`）做校验；时间边界改为从 AST 抽取对 `time_field` 的比较表达式；`_context_table_coverage` 收窄到 `query_plan["entities"]`（Inspector 已查过，这个检查其实可以删）。

### 3.3 评测指标失真：默认跑分优化的是错误目标

`run_eval.py` 中 `answer_match is not False` 在无期望答案时空洞通过，标准 20 题集没有一题带 ground-truth 答案，于是"严格通过率 95%" 对上真实基线的 26%。同时表/关键词匹配是对原始 SQL 的朴素子串匹配（期望表 `users` 能被列名 `users_snapshot` 匹配上；`paid` 匹配 `paid_at`），失败归因也因此不可靠。另外 4 个失败用例全部 `present_in_context: 1`——表已检索进上下文但模型没用，说明当前短板在生成而非检索。

**建议**：给标准集补齐 `expected_answer/expected_rows`（schema 已支持）；无答案校验时 `semantic_accuracy_rate` 输出 `null` 而不是 `0`；表/关键词匹配改用 sqlglot 解析真实表引用与函数调用。指标校准应先于一切"优化"。

### 3.4 认证默认全开放 + 限流器缺陷

`AUTH_REQUIRED=false`（.env.example 默认值）时任何匿名请求都获得 **admin** 主体（`dependencies.py` 11~18 行），`validate_security()` 只在 `APP_ENV=production` 才拦，且其中 Redis 检查因 `redis_url` 有非空默认值而是死代码。限流器方面：内存回退分支的 `_memory_attempts` 字典永不清理（撞库攻击下无限增长）、按进程计数（多 worker 时限额 ×N）、且成功登录也计数（15 分钟内 10 次正常登录会把合法用户锁住）。`require_csrf` 与 `get_current_principal` 各查一遍会话（每个写请求 2 次完整 DB 查询），`touch_session` 每个请求都写库。

**建议**：默认只绑定 127.0.0.1；开发主体默认角色降为非 admin；会话解析结果缓存在 `request.state`；`touch_session` 改为 `last_seen_at` 超过 60 秒才更新；限流器只计失败次数并给内存分支加 TTL 淘汰。

## 四、P1：中优先级

**服务与数据层。** `embedding_sync_service.py` 的 schema/metric 同步没有 `WHERE embedding IS NULL` 或内容哈希判断，每次 refresh 全量重付 embedding 费（sql_memory 分支反而做对了，照抄即可）；会话列表 `list_for_owner` 反序列化整个 JSONB（最多 200 条消息）只为取标题时间戳，改为只 SELECT 已冗余的列；每次 LLM/embedding 调用都新建 `httpx.Client`（丢失 keep-alive/TLS 会话），应改为模块级共享实例，且 4xx 确定性错误（401/404/422）不应重试；`model_adapter` 的重试用 `time.sleep` 阻塞线程。检索路径上多处 `except Exception: return {}` 静默吞错（`vector_retrieval.py`、`context_builder.py` 的 FK 加载）——pgvector 索引坏了或维度不匹配时，系统表现为"检索质量神秘变差"而无任何日志，至少加 `logger.warning(exc_info=True)` 并在诊断里标 `degraded: true`。索引方面需确认：`auth_sessions(token_hash)`、`conversation_states(owner_id, updated_at DESC)`、`sql_memories(normalized_question)` 唯一索引，以及三张 embedding 表的 HNSW/IVFFlat 索引（没有 ANN 索引时每次 `<=>` 都是全表排序）；过期会话/审计/运行日志无任何清理任务，表会无限增长。

**前端。** 开发页跑在 `127.0.0.1:3000` 而 API 默认 `http://localhost:8000`——Cookie 认证下 localhost 与 127.0.0.1 在部分浏览器是两个 Cookie 罐，会出现"随机掉登录/CSRF 失败"；建议 vite 加 `server.proxy` 走同源，`API_BASE_URL` 默认空串。ECharts 全量引入且无路由懒加载、无 manualChunks，入口包白白多约 350KB gzip——改 `echarts/core` 按需注册 + `React.lazy` 分包。`@tanstack/react-query` 在依赖里但全项目零引用，而 `EvaluationDashboard` 和 `QueryHistoryTable` 手写了两份一模一样的 fetch 逻辑——要么用起来要么删掉。`ChatPage.tsx`（509 行、11 个 useState）建议拆出 `useConversations()`/`useChatStream()` 两个 hook 和侧栏/消息列表组件，SSE stage 事件目前每次 map 整个消息数组。全应用没有 error boundary，一个畸形的图表 spec 会白屏整页。SSE 客户端无空闲超时（模型挂起时 `reader.read()` 永久阻塞）且只读第一行 `data:`，不符合 SSE 规范。消息 ID 用 `Date.now()` 同毫秒会撞，换 `crypto.randomUUID()`。

**评测体系。** run_eval.py 严格串行且单用例无超时，50 题要 17+ 分钟，checkpoint/batch 机制其实是在绕自己的慢——准确率评测加 `--workers N` 并行 + 单用例硬超时，延迟评测保留单 worker 模式。run 与用例的关联靠"问题文本匹配最近 5 条 run"（重复问题/并发即静默失效，报告里 stage 统计只有 19/20 正是这个原因）——让 `/api/analyze` 直接在响应里返回 `run_id`。报告 JSON 把同一用例在 failures/assertion_failures/implementation_failures/cases 里重复序列化 4 次（91.6KB / 20 题）。n=1 的 speed 探针和 n=3 的 warm 对比不足以支撑"router 修复后变快""-52.36%"这类结论，加 `--repeat N` 输出均值 ± p95。

## 五、P2：代码质量与工程规范

`analysis_graph.py`（1317 行）集编排、业务 lint、关键词表、日志扇出于一身，`_log_analysis_run` 有约 35 个关键字参数——建议拆出 `tools/sql_intent_validator.py` 并把日志函数改为接收 state。跨模块逐字重复的代码已在漂移：`_required_tables_for_question`（两处）、`_loads_json_object`（三处）、`_table_aliases`（两处且一处 lowercase 一处不——真实行为分歧）、指标/维度关键词表三处内容不一致（"州/state" 在 parser 里是维度、在 graph 里缺失）——收敛到 `business_vocabulary.py` / `json_utils.py` / 共享 sqlglot 工具。死代码：`_select_generated_sql_compat` 的 TypeError 兜底不可达；`_test_adapter` 只有 repair 节点传、TypedDict 里没有；`run_eval.py` 的 `analyze_with_test_client` 无人调用。`analysis_presenter.py` 硬编码 `"toolCalls": 8, "modelCalls": 0` 和全部 `"time": "1ms"`，而真实的 `node_timings` 已经采集却没传给 presenter——前端展示的 trace 是假数据。每个候选 SQL 被 sqlglot 重复 parse 6~10 次，parse 一次传 AST 即可。

工程面：根 `package.json` 所有脚本硬编码 `.venv\Scripts\python`，任何 Linux CI 都跑不了（项目目前也确实没有 CI）；`requirements.txt` 全部 `>=` 无锁文件，构建不可复现（langgraph 尤其快迭代）；`load_dotenv("backend/.env")` 是相对 CWD 的路径，换目录启动即静默丢配置，且 `config.py` 里 `override=True` 会让文件覆盖真实环境变量；`eval/reports/` 下 70+ 个时间戳 JSON 与 checkpoint 混在一起，建议 gitignore 掉、只保留 `baselines/` 精选目录；`docs/evaluation.md` 引用了本机桌面路径 `C:\Users\admin\Desktop\新建 文本文档.txt` 作为 ground-truth 出处（简历项目建议清掉），且文中"执行 8/20"与仓库里 19/20 的报告对不上号；`docs/data_model.md` 只写到迁移 004 而实际已到 016，且迁移序号缺 010——需确认 init_db 的排序是数字序而非字典序。`空 question 会被静默替换成演示问题（agent_service.py 51 行）应改为 422。

## 六、建议路线图

**第一步（先校准仪表盘再踩油门）**：修评测——标准集补 ground-truth 答案、指标空值语义、sqlglot 化匹配（§3.3）；给未归因的 5.2 秒加计时（§2.4）。约 1~2 天，此后所有优化都有可信数字。

**第二步（延迟减半）**：embedding 复用（§2.1）+ 连接池与日志批量（§2.2)+ memory_update 异步化 + 跳过冗余 router 调用（§2.3）。都是局部改动，合计预期 P50 从约 19.8s 降到 10s 上下。

**第三步（正确性）**：Guard 的 AST 写检查（§3.1）、意图校验 AST 化消除假阳性修复循环（§3.2）、记忆命中策略复盘（§2.5）。这一步直接作用于 26% 的真实严格通过率。

**第四步（加固与整理）**：认证默认值与限流器（§3.4）、前端同源代理与分包、eval 并行化、代码去重与目录清理（§4、§5）。
